## Context

### Goal
Full project refactor covering: lint-staged + git hooks, oxlint/oxfmt tooling, component extraction (<400 LOC), BFF controller/service layering, frontend state domain aggregation, and React Router layout Outlet pattern.

### Scope In
1. **Lint-staged + Git hooks**: Add `lint-staged` + `husky`, run oxlint + oxfmt on staged files, run incremental vitest (--changed) and playwright tests on commit
2. **Oxlint + Oxfmt**: Replace absent ESLint/Prettier with `oxlint` + `oxc-format` (aka `oxfmt`) as sole lint/format tools
3. **Component extraction**: Enforce <400 LOC per file; currently only `apps/bff/src/usage.ts` (1075 lines) exceeds this
4. **BFF architecture**: Introduce controller/service layers to `apps/bff`, aggregate types for reuse
5. **Frontend state aggregation**: Consolidate duplicated data-fetching hooks (`useDashboardData`, `useProviderInsightsData`) into a shared domain store
6. **Router layout**: Add a proper dashboard layout route using `@tanstack/react-router` `Outlet` pattern, replacing manual `DashboardPageLayout` wrapper calls
7. **Additional improvements**: Remove dead `eslint-disable` comments, align test runner scripts

### Scope Out
- No visual/design changes to the UI
- No migration away from @tanstack/react-router to another router
- No migration away from Jotai to another state library
- No changes to `packages/shared` API surface (types stay stable)
- No Playwright E2E test authoring (existing E2E tests at `e2e/dashboard.spec.ts` must stay passing)

### Existing Code

#### Monorepo
- pnpm workspace: `apps/web`, `apps/bff`, `packages/shared`
- No turborepo/nx; root scripts use `pnpm -r`
- packageManager: pnpm@10.30.3

#### Frontend (apps/web)
- Vite + React 19 + @tanstack/react-router (explicit code routes in `main.tsx`)
- Jotai for global state (`atoms.ts` — 63 lines, 30+ atoms)
- Two separate data hooks: `useDashboardData` and `useProviderInsightsData` that duplicate auto-refresh logic, loading/error state management, and both write to the same global atoms (summaryAtom, providerInsightsAtom, etc.)
- Layout via manual `DashboardPageLayout` wrapper component, no `Outlet` nesting
- All route components: `rootRoute` → each page directly; no intermediate layout route
- Largest file: `shared.tsx` (332 lines) — within limit

#### BFF (apps/bff)
- Hono framework, all routes in `app.ts` (177 lines)
- Core logic in `usage.ts` (1075 lines) — needs splitting
- `pricing.ts` (389 lines) — near limit but acceptable
- `messages.ts` — message analytics
- No controller/service separation; `app.ts` directly calls usage/pricing/messages functions

#### Testing
- Vitest for both web and bff (14 test files total across web and bff)
- Playwright E2E tests exist: `e2e/dashboard.spec.ts` (4 tests), `e2e/fixtures.ts` (mock data factories)
- `playwright.config.ts` at root, uses `pnpm dev:web` as webServer, targets localhost:3000
- Root scripts: `test` (vitest), `test:e2e` (playwright)

#### Linting/Formatting
- No ESLint/Prettier/Biome/Oxlint config files
- `lint` scripts just run `tsc --noEmit`
- Multiple stale `eslint-disable` comments in source
- `.git/config` has `hooksPath = .husky/_` but no .husky directory

### Dependencies
- `usage.ts` is the core data pipeline; splitting it affects `app.ts` imports
- `atoms.ts` is imported by all page components and data hooks
- `main.tsx` route tree affects all pages
- shared package types are stable API contract between web and bff

### Constraints
- pnpm monorepo; all tool installs via pnpm
- Must keep existing vitest test suites passing
- TypeScript strict mode in all packages
- @tanstack/react-router (not react-router-dom) — use its `Outlet` + layout routes

### Decisions
1. **Oxlint over ESLint**: User requirement; oxlint is Rust-based, fast, good for lint-staged
2. **Oxfmt over Prettier**: User requirement; oxfmt = `oxc-format` CLI, part of oxc toolchain
3. **Controller/Service pattern in BFF**: Thin controllers (route handlers) delegate to service functions
4. **Domain-aggregated state**: Single data hook with shared refresh logic, split atoms by domain
5. **Layout route**: Add `dashboardLayoutRoute` with Outlet between rootRoute and page routes

### Assumptions
- oxlint and oxc-format are available as npm packages (`oxlint`, `oxc-format`)
- Vitest `--changed` flag works with pnpm workspace for incremental testing
- @tanstack/react-router supports nested layout routes with Outlet (confirmed from main.tsx existing usage)

### Risks
- **usage.ts splitting**: High coupling between internal functions; need careful interface design
- **State consolidation**: Changing data hooks could break existing page behavior
- **Route restructure**: Moving to layout routes changes component mount lifecycle

## Phase 4: Router Layout with Outlet + Reusable Layout Components

### Analysis: Layout Similarity
- `detail-page` and `session-detail-page` share nearly identical structure:
  - `DetailStickyHeader` (back button, title, theme toggle, refresh)
  - `DashboardPageLayout variant="wide"`
  - Error panel (same pattern)
  - Content area with max-w-[54rem] centered card container
  - Both use `px-6 sm:px-8 lg:px-10` padding pattern
- `overview-page` and `providers-page` share:
  - `StickyHeaderShell` + `ControlBar` (same props: range, customDateRange, refresh)
  - `DashboardPageLayout` default variant
  - Error panel (same pattern)
- `HorizontalPanelRail` is already extracted, used in session-detail

### 4.1 Create route hierarchy with Outlet
```
rootRoute (theme effect)
  └── dashboardLayoutRoute (id: 'dashboard', Outlet)
        ├── overviewRoute (/overview)
        ├── providersRoute (/providers)
        └── detailLayoutRoute (/detail, Outlet for nested detail pages)
              ├── dayDetailRoute (/detail/$date)
              └── sessionDetailRoute (/detail/$date/$session)
```

### 4.2 Create reusable layout components
1. **`DashboardShell`** — replaces current `DashboardPageLayout`:
   - Accepts `variant: 'default' | 'wide'`
   - Renders `<main>` with bg/text + `<Outlet />` or children
   - Used as dashboard layout route component

2. **`ListLayoutShell`** — new shared layout for overview/providers:
   - Includes `StickyHeaderShell` + `ControlBar`
   - Shared range/refresh state (from atoms, no prop drilling)
   - Children get rendered below the control bar

3. **`DetailLayoutShell`** — new shared layout for detail/session-detail:
   - `DetailStickyHeader` with configurable back link, title
   - Shared `variant="wide"` DashboardPageLayout
   - Error panel pattern
   - Centered card container (`mx-auto max-w-[54rem]`) as reusable slot
   - Scrollable panel rail support

### 4.3 Simplify page components
- Pages become pure content renderers, no layout wrapper calls
- Detail and session-detail pages only render their domain-specific content
- Overview and providers pages only render their metric/chart content
